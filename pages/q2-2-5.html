先读整体，再逐行理解

全体计数仍需读24000人，仍Seq Scan→HashAggregate→Sort。按域名排序的键也不能预先知道哪个域名COUNT最大，因此不能直接满足ORDER BY COUNT(*) DESC。

  1. L1-- Report the domain-count query plan after creating the expression index.

    注释标明已建立表达式索引；全表分组仍须处理所有会员，计划可能继续选择顺序扫描。

    Source comment: Report the domain-count query plan after creating the expression index.

  2. L2EXPLAIN (ANALYZE, BUFFERS)

    EXPLAIN 修饰紧接着的 SQL，输出物理计划；ANALYZE 会真正运行它并记录 actual time、rows 和 loops，BUFFERS 记录缓冲页访问。结果是计划文本而非普通结果表；cost 是优化器估计单位，不能当成毫秒，也不能将父子节点耗时简单相加。

    Execute the following query to collect its actual plan and buffer use; estimated cost is not milliseconds.

  3. L3SELECT LOWER(SPLIT_PART(email, '@', 2)) AS provider_domain,

    先用 SPLIT_PART(email,'@',2) 按 @ 分隔取第二部分，再用 LOWER 转小写，命名为 provider_domain。它规范域名大小写，不能仅靠完整 email 的排序替代；格式异常的邮箱需另作数据校验。

    Extract the second @-separated field and lowercase it as provider_domain.

  4. L4 COUNT(*) AS member_count

    COUNT(*) 数每个规范化域名下的成员行，输出名为 member_count。每位成员一行，即使 local part 不同，只要域名相同也会进入同一组。

    COUNT(*) counts member rows per normalized domain as member_count. Different address prefixes still contribute to the same domain group.

  5. L5FROM MEMBERS

    从 MEMBERS 读全部成员。这里没有稀有域名 WHERE，因为问题要求统计所有不同 provider，而不只某一家。

    Read every member from MEMBERS. There is no rare-domain WHERE because the question asks for all providers.

  6. L6GROUP BY LOWER(SPLIT_PART(email, '@', 2))

    按同一个 LOWER(SPLIT_PART(...)) 表达式分组。若只在 SELECT 中 LOWER、分组却用原字符串，大小写变体仍可能先被拆成不同组。

    Group by exactly the same normalized expression. Normalizing only the displayed SELECT value would not correctly merge groups formed from differently cased raw strings.

  7. L7ORDER BY member_count DESC, provider_domain;

    按 member_count 降序把最常用域名排前；同人数按域名升序。最终 12 组共覆盖 24,000 人；索引按域名排序也不能直接提供按人数排序。

    Sort counts descending and domain names ascending for ties. Twelve groups cover 24,000 members; domain index order does not directly order aggregate counts.

  8. L8（空行）

    空行用于把相邻语义块分开，帮助区分输入、处理或独立语句；不执行 SQL、不提交事务，也不会重置配置。

    A visual separator only; it executes no statement and changes no transaction or setting.

  9. L9-- Report the selective lookup plan for a rare provider domain.

    注释切换为稀有域名等值检索；与上一条全表分组的选择率不同，正好说明索引何时更有价值。

    Source comment: Report the selective lookup plan for a rare provider domain.

  10. L10EXPLAIN (ANALYZE, BUFFERS)

    EXPLAIN 修饰紧接着的 SQL，输出物理计划；ANALYZE 会真正运行它并记录 actual time、rows 和 loops，BUFFERS 记录缓冲页访问。结果是计划文本而非普通结果表；cost 是优化器估计单位，不能当成毫秒，也不能将父子节点耗时简单相加。

    Execute the following query to collect its actual plan and buffer use; estimated cost is not milliseconds.

  11. L11SELECT member_id, member_name, email

    稀有域名查询需要会员编号、姓名和原邮箱，而表达式索引只存域名键和行位置；因此找到匹配后通常还要读取表行，而非假定索引覆盖全部输出。

    Project ID, name and original email for the rare-domain lookup.

  12. L12FROM MEMBERS

    从 MEMBERS 读全部成员。这里没有稀有域名 WHERE，因为问题要求统计所有不同 provider，而不只某一家。

    Read every member from MEMBERS. There is no rare-domain WHERE because the question asks for all providers.

  13. L13WHERE LOWER(SPLIT_PART(email, '@', 2)) = 'exemail.com.au';

    只保留规范域名等于 exemail.com.au 的会员；表达式与 IDX_MEMBER_DOMAIN 定义一致。该谓词有机会使用表达式索引定位少量匹配行，但是否采用 Bitmap/Index/Seq Scan 要看该版本实际计划，不能只凭 SQL 断言。

    Filter the same normalized expression as the index; the actual access path comes from the plan.

聚合函数

COUNT · 计数

COUNT(*) / COUNT(expression)

输入一组行，返回bigint计数；*计所有行，expression只计表达式非NULL行。

本作业中的作用
Q1.1统计每类车每站的Collect事件；Q2.2统计每个域名会员。
输入与输出示例
教学：amount为10、NULL、20时，COUNT(*)=3，COUNT(amount)=2。
边界与常见错误
空输入COUNT返回0。COUNT(DISTINCT vehicle_id)会变成不同车辆数，不能代替取车次数。
相关题目：Q1.1.1 · Q1.1.2 · Q2.1.3 · Q2.2.1 · Q2.2.2 · Q2.2.5
字符串函数

LOWER · 转小写

LOWER(text) → text

输入文字，按适用排序/字符规则返回小写文字；NULL输入返回NULL。

本作业中的作用
规范化域名，使Bigpond.com与bigpond.com归入同组和同索引键。
输入与输出示例
教学：LOWER('Bigpond.com')='bigpond.com'。
边界与常见错误
它不验证邮箱格式，不去空格，也不自动修复拼写；与Unicode/locale有关的生产需求须另外设计。
相关题目：Q2.2.1 · Q2.2.2 · Q2.2.3 · Q2.2.4 · Q2.2.5
字符串函数

SPLIT_PART · 按分隔符取段

SPLIT_PART(email, '@', 2) → text

三个参数：原文本、分隔文本、从1起的段号。返回所选段。

本作业中的作用
取每位会员邮箱@之后第二段，外包LOWER得到规范化域名。
输入与输出示例
教学：SPLIT_PART('a@X.com','@',2)='X.com'。
边界与常见错误
无@则第二段为空字符串；多@只取第2段；参数NULL则返回NULL。NOT NULL UNIQUE不保证邮箱合法。
相关题目：Q2.2.1 · Q2.2.2 · Q2.2.4 · Q2.2.5
DDL语法

Expression index · 表达式索引

CREATE INDEX IDX_MEMBER_DOMAIN ON MEMBERS ((LOWER(SPLIT_PART(email,'@',2))));

以计算结果而非原列作为索引键；写入时维护，查询语义表达式要与键相匹配。

本作业中的作用
从完整email索引转为规范化域名键，支持稀有域名查找。
输入与输出示例
教学：a@X.COM与b@x.com索引键同为x.com。
边界与常见错误
不是每个含表达式的聚合都加速；全体人数统计仍要读全体。函数须符合不可变性等索引条件。
相关题目：Q2.2.3 · Q2.2.4 · Q2.2.5
语句与选项

EXPLAIN / ANALYZE / BUFFERS · 观察真实工作

EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

EXPLAIN只显示规划；加ANALYZE实际执行并给出测量；BUFFERS显示缓冲访问。

本作业中的作用
本作业比较计划成本、估计/实际行数、耗时与页访问。
输入与输出示例
教学：cost=0..10 rows=2，actual time=0.1..0.2 rows=6 loops=1，表示估2实6，成本不是0.2毫秒。
边界与常见错误
EXPLAIN ANALYZE会真的执行语句；用于修改语句时也会产生修改。BUFFERS父节点通常包含子节点，不重复求和。
相关题目：Q1.1.2 · Q1.3.2 · Q2.1.2 · Q2.1.3 · Q2.2.2 · Q2.2.5 · Q3.1.2 · Q3.2
执行统计

Buffers / heap blocks / hit / read

Buffers: shared hit=n read=m; Heap Blocks: exact=k

hit在PostgreSQL共享缓冲中找到；read需把页读入共享缓冲，仍可能由操作系统缓存服务；exact位图保留精确行位置。

本作业中的作用
Q3.2区分C1读31页与C2全hit；D2读全部1636heap块还读索引。
输入与输出示例
教学：shared hit=1659不一定是1659个唯一物理页，可能包含重访和子节点。
边界与常见错误
read不保证真正磁盘IO；不要把行选择率当页覆盖率。lossy若出现需重查整页，但本六图heap均报告exact。
相关题目：Q2.1.3 · Q2.2.5 · Q3.2
物理执行节点

Seq / Index / Bitmap / Index Only Scan

Seq Scan; Bitmap Index Scan → Bitmap Heap Scan

Seq逐页检查表；Index从键定位再取行；Bitmap先收位置再按heap页取；Index Only要求足够列与可见性条件。

本作业中的作用
全时段Collect可顺扫，少量Incident适合bitmap；稀有域名仍回heap取姓名。
输入与输出示例
教学：1000行取3行可定位，取950行常顺读省额外索引工作。
边界与常见错误
少量行可能散在很多页；Index Only也可能有Heap Fetches。不能只看“有索引”推断计划。

Explanation 
The domain-count query keeps its Seq Scan -> HashAggregate -> Sort plan, estimates 
24,000 groups and returns 12. Its top cost stays 2864.09..2924.09; execution is 5.274 ms 
compared with 6.997 ms before the index. All 24,000 members still have to contribute to the 
counts, and an index ordered by domain cannot directly satisfy ORDER BY COUNT(*) 
DESC. 
The rare-provider lookup instead uses Bitmap Index Scan on IDX_MEMBER_DOMAIN 
followed by Bitmap Heap Scan. It returns 248 members, about 1.03 percent of MEMBERS, 
versus 120 estimated, with cost 5.22..226.08 and execution time 0.510 ms. The bitmap 
batches access to 164 exact heap blocks; heap access is needed for member_id, 
member_name and email. The index avoids evaluating the domain predicate on every 
member. Its advantage is selective access, rather than speeding every query that mentions 
the expression.

从要求推到结论

全体计数仍需读24000人，仍Seq Scan→HashAggregate→Sort。按域名排序的键也不能预先知道哪个域名COUNT最大，因此不能直接满足ORDER BY COUNT(*) DESC。

教学例：1000人归10域名，统计仍要每人贡献；某域只有3人则可从索引直达3个位置。是否获益取决于工作量而不是函数名字。

检查理解

为什么域名索引有序仍不能直接返回“人数最多在前”？

展开参考答案

索引顺序是域名字符串顺序；人数是汇总后才产生的值。必须先统计，再按COUNT排序。

再检查一个关键点

Bitmap Heap Scan为什么还要拿member_name和email？

我对题目的理解是：同一文件需要两个EXPLAIN，不能只展示有利的稀有查找。比较全体聚合与选择性查找，不是比较“有函数”与“没有函数”。 实现时，全体计数仍需读24000人，仍Seq Scan→HashAggregate→Sort。按域名排序的键也不能预先知道哪个域名COUNT最大，因此不能直接满足ORDER BY COUNT(*) DESC。 从证据看，主报告p23–24完整重放：聚合cost2864.09..2924.09、实际12组、5.274ms（索引前6.997ms）；稀有查找cost5.22..226.08、估计120实际248、0.510ms。保留单次计时，不推断稳定比例。 我还会说明这个边界：根SQL不再有旧completed版独立打印248行的SELECT，而保留两个ANALYZE计划；ANALYZE本身执行了查询，其rows可以证明行数，但报告普通结果应按原题展示约定说明。
