LEARN

一行、一列、一张表

表（table）是一类事物的集合；行（row）是一件具体记录；列（column）是记录的属性。VEHICLES一行是一辆实体车，MODELS一行是一种规格，BOOKING_EVENTS一行是一次事件。不要把“一辆车”和“一次取车”当同一计数单位。

教学例：VEHICLES(V1,MD1,S1)、MODELS(MD1,Sedan)、STATIONS(S1,南站)。一条事件(V1,Collect)只有车辆ID，经两次关联才知道它属于Sedan、南站。这些简化数据只用于教学，不是课程真实输出。

书写先SELECT输出列，再FROM数据来源、WHERE条件、ORDER BY顺序、LIMIT数量。理解时先问从哪张表读→哪些行留下→取哪些列→怎样排序→留几行。该例取最新三个Collect事件，而不是取每辆车最新事件，二者不同。

复杂查询的逻辑阶段为FROM/JOIN→WHERE→GROUP BY/聚合→HAVING→窗口→SELECT→ORDER BY→LIMIT。HAVING是补充知识，当前原答案未使用。优化器可重排物理工作，在不改变语义前提下选择hash、bitmap、并行等；不能把逻辑顺序当实际节点顺序。

单引号'Collect'是文字；e.vehicle_id中的e是别名、点号取列；AS给结果起名；分号结束SQL；--直到行末为注释；圆括号可能是函数参数、子查询或CTE。NULL是未知/缺失，不能写= NULL，应写IS NULL。

从叶扫描向父节点追踪行如何变化：扫描哪些表、条件留几行、连接是否放大、聚合成几组、最终输出多少。再看cost预测、actual实测、loops、buffers及最终Planning/Execution。

两个连接：可见性与等待

连接是独立服务器会话，可用pg_backend_pid核对。BEGIN后改动在提交前属于该事务；COMMIT成功才提交。错误后事务可能进入失败状态，COMMIT结果实际ROLLBACK。SAVEPOINT仅建恢复点，原Q4未ROLLBACK TO。

READ COMMITTED每条命令取新快照；快照是已提交内容的一致视图，不是车的预留锁。普通SELECT仍拿兼容ACCESS SHARE表锁，与另一会话插入不冲突。UPDATE对冲突行加锁持有到事务结束。

一个等待者仍可能等到对方提交；两者各持对方所需的锁形成有向环才是死锁。数据库会中止某受害事务，受害者先前修改也撤销。

Q4公共背景 · 完整中英对照

作业要求PDF p7 · Q4 Transactions (9 marks total)

In PostgreSQL, a transaction is set up by surrounding the SQL commands of the transaction with BEGIN and COMMIT commands. For example, a banking transaction would look like: BEGIN; UPDATE accounts SET balance = balance - 100.00 WHERE name = 'Alice'; -- some more statements etc etc COMMIT; https://www.postgresql.org/docs/current/tutorial-transactions.html In this question we will examine what happens when two transactions occur concurrently. Background: how PostgreSQL reads You have seen two ways of keeping a concurrent schedule serialisable: locking protocols such as two-phase locking, and timestamp ordering. PostgreSQL uses neither of these for ordinary reads, so what you are about to observe will not follow from either one directly. This section gives you what you need; you are not expected to have met it before. Instead of taking read locks, a PostgreSQL query reads from a snapshot — a consistent picture of the database containing exactly those changes that were committed before the snapshot was taken. Because reading acquires no locks, readers never block writers and writers never block readers. At PostgreSQL's default isolation level, READ COMMITTED, a new snapshot is taken at the start of every statement. Two statements in the same transaction may therefore see different data, if another transaction committed in between them. Two consequences are worth holding on to as you work through this question: • A trigger runs inside the transaction that fired it. Any query the trigger makes is answered from that transaction's current snapshot. It gets no special or privileged view of the database. • A snapshot is not a lock. Reading a row records nothing and reserves nothing; it does not prevent another transaction from changing what you just read.

作业要求p7原页图

在PostgreSQL中，用BEGIN和COMMIT包围一组SQL命令来建立事务。例如银行事务先BEGIN，再执行UPDATE accounts SET balance = balance - 100.00 WHERE name = 'Alice';，可含更多语句，最后COMMIT。原文给出PostgreSQL事务教程链接。本题考察两个事务并发时会怎样。

背景：PostgreSQL如何读取。你已学过两种使并发调度可串行化的方法：两阶段锁等加锁协议，以及时间戳排序。PostgreSQL的普通读取并不采用上述两者之一，所以接下来的观察不能直接从它们推导。本节提供必要背景，不要求你已学过。

PostgreSQL查询读取一个快照（snapshot），即数据库的一致图像，包含在快照取得之前已提交的那些变化，而不是通过取得读锁读取。原题接着说：因为读取不加锁，读者不会阻塞写者，写者也不会阻塞读者。

在PostgreSQL默认隔离级别READ COMMITTED下，每条语句开始时都会取得新快照。因此，同一事务的两条语句可能读到不同数据：另一事务可能在两者之间已经提交。

处理本题时记住两个推论：触发器在引发它的事务中运行，其发出的查询由该事务当前快照回答；它没有特殊或特权视角。快照不是锁：读取一行不会记录或预留任何东西，不能阻止另一事务改变你刚读到的内容。

补充解释，与忠实翻译分开

上面保留了原题“读取不加锁”的教学简化。普通SELECT仍拿ACCESS SHARE表锁，但不因此取得预留车辆的冲突行锁；某些DDL表锁仍可能与读取相互阻塞。快照的完整规则还包括可见的自身修改，不能将原题简化描述理解为忽略自己的写入。
