先读整体，再逐行理解

A对每辆v检查是否存在e.vehicle_id=v.vehicle_id且event_type=Collect的事件。子查询SELECT 1只是存在性占位，找到匹配就足够；NOT EXISTS保留一个也没有的车辆。

  1. L1-- Statement A: find vehicles with no Collect event using NOT EXISTS.

    注释标记写法 A：寻找没有任何 Collect 记录的车辆，不等同于最近一条事件不是 Collect。

    Source comment: Statement A: find vehicles with no Collect event using NOT EXISTS.

  2. L2SELECT v.vehicle_id

    输出候选车辆的唯一编号。Statement A 用 NOT EXISTS 保留无 Collect 的车；Statement B 通过左连接后检查未匹配的 NULL 行实现同一目标。

    Project IDs of vehicles that pass the anti-join condition.

  3. L3FROM VEHICLES v

    从完整 VEHICLES 表出发，包含没有事件或只有预约/取消事件的车辆。若从 Collect 日志出发，反而找不到“从未出现”的车辆。

    Start from the entire fleet, including vehicles with no events or only reservations/cancellations. Starting from Collect events would omit the very absences being sought.

  4. L4WHERE NOT EXISTS (

    NOT EXISTS 要求括号内找不到任何匹配行。它回答“是否不存在一次 Collect”，而不是检查车辆的最后一个事件。

    NOT EXISTS requires no matching inner row. It tests absence of any Collect, not merely the type of the latest event.

  5. L5 SELECT 1

    相关子查询只需回答“是否存在匹配取车事件”，不需要事件具体列。SELECT 1 的常量不是统计次数，也不限制最多只扫描一行；EXISTS 检查存在性，优化器可改写为反连接。

    Select an irrelevant constant for the existence test; it does not count events.

  6. L6 FROM BOOKING_EVENTS e

    子查询从事件日志读取，别名 e；后面的 e.vehicle_id = v.vehicle_id 把它与当前候选车辆关联，并只检查 Collect 类型。

    Read event rows as e, correlated with the candidate vehicle.

  7. L7 WHERE e.vehicle_id = v.vehicle_id

    只看与外层这辆 v 相同 vehicle_id 的事件，形成相关子查询。如果漏掉相关条件，一辆车被取用就可能让所有候选都被排除。

    Correlate inner events to the current outer vehicle. Omitting this condition could make one Collect event incorrectly disqualify every candidate.

  8. L8 AND e.event_type = 'Collect'

    在 NOT EXISTS 子查询的 WHERE 中继续要求事件类型为 Collect。它与前一行 vehicle_id 相等条件同时成立；子查询只要找到这样一条取车事件，外层这辆车就不满足 NOT EXISTS。这里不是 LEFT JOIN 的 ON 条件。

    Filter Collect inside the correlated subquery; any such match makes NOT EXISTS false.

  9. L9)

    关闭 NOT EXISTS 子查询。这个逻辑相关性不强制物理计划逐车完整重扫；优化器可以改写成 anti-join。

    Close the NOT EXISTS subquery. Logical correlation does not force a full rescan per vehicle; the optimizer can transform it into an anti-join.

  10. L10ORDER BY v.vehicle_id;

    按车辆编号排序，便于稳定比较两种写法的完整结果；若本段前面有 EXPLAIN，本排序也会体现在计划中。没有 ORDER BY 时 SQL 不保证返回顺序相同，具体结果行数应查对应版本证据。

    Order vehicle IDs for result comparison, or include that order in the explained plan.

  11. L11（空行）

    空行用于把相邻语义块分开，帮助区分输入、处理或独立语句；不执行 SQL、不提交事务，也不会重置配置。

    A visual separator only; it executes no statement and changes no transaction or setting.

  12. L12-- Statement B: find the same vehicles using a left join and a NULL check.

    注释标记等价写法 B：保留全部候选车辆，匹配 Collect，再留下没有匹配事件的 NULL 扩展行。

    Source comment: Statement B: find the same vehicles using a left join and a NULL check.

  13. L13SELECT v.vehicle_id

    输出候选车辆的唯一编号。Statement A 用 NOT EXISTS 保留无 Collect 的车；Statement B 通过左连接后检查未匹配的 NULL 行实现同一目标。

    Project IDs of vehicles that pass the anti-join condition.

  14. L14FROM VEHICLES v

    从完整 VEHICLES 表出发，包含没有事件或只有预约/取消事件的车辆。若从 Collect 日志出发，反而找不到“从未出现”的车辆。

    Start from the entire fleet, including vehicles with no events or only reservations/cancellations. Starting from Collect events would omit the very absences being sought.

  15. L15LEFT JOIN BOOKING_EVENTS e

    LEFT JOIN 保留左侧的所有车辆。匹配不到右侧事件时，右侧的 e 列会被补成 NULL，为后面的未匹配检查提供依据。

    LEFT JOIN preserves every vehicle, filling right-side event columns with NULL when no matching event exists.

  16. L16 ON e.vehicle_id = v.vehicle_id

    连接条件先限定事件属于同一辆车。此条件决定哪些事件能和车辆配对，不是在最终结果上检查 NULL。

    The first ON condition pairs an event with the same vehicle. It defines matches before the later unmatched-row filter.

  17. L17 AND e.event_type = 'Collect'

    Collect 条件继续放在 ON 中，只把取车事件视作匹配。若把它移到 WHERE，无匹配行的 e.event_type 为 NULL，会被过滤掉，破坏反连接语义。

    Keep the Collect predicate inside ON. Moving it to WHERE would discard unmatched rows with NULL event_type and break the anti-join.

  18. L18WHERE e.vehicle_id IS NULL

    e.vehicle_id 在真实事件中 NOT NULL，所以这一列为 NULL 能可靠识别 LEFT JOIN 没有匹配的车辆。匹配过 Collect 的车辆不会通过这个条件。

    Real event vehicle_id values are NOT NULL, so NULL here reliably identifies an unmatched vehicle. Vehicles having a Collect match fail this condition.

  19. L19ORDER BY v.vehicle_id;

    按车辆编号排序，便于稳定比较两种写法的完整结果；若本段前面有 EXPLAIN，本排序也会体现在计划中。没有 ORDER BY 时 SQL 不保证返回顺序相同，具体结果行数应查对应版本证据。

    Order vehicle IDs for result comparison, or include that order in the explained plan.

关键字

JOIN / ON / 别名 · 补齐关联属性

FROM BOOKING_EVENTS e JOIN VEHICLES v ON v.vehicle_id=e.vehicle_id

内连接保留符合ON的行对；e/v是查询局部别名，点号取对应表列。

本作业中的作用
事件没有body_type和station_name，必须经车辆到车型和站点。
输入与输出示例
教学：事件(V1,Collect)与车辆(V1,MD1,S1)连接后才知道车型和站点ID。
边界与常见错误
目标主键唯一避免此连接成倍放大事件。漏写连接条件会形成笛卡尔积；同名列要写别名前缀。
相关题目：Q1.1.1 · Q1.2 · Q3.1.1
关键字

LEFT JOIN / NULL 扩展

VEHICLES v LEFT JOIN BOOKING_EVENTS e ON ... WHERE e.vehicle_id IS NULL

左边每辆车至少保留；右边无匹配时填NULL。

本作业中的作用
Q3只让Collect参与匹配，再保留完全没Collect的车辆。
输入与输出示例
教学：V2只有Reserve，ON中限定Collect后无匹配，所以e.vehicle_id为NULL，V2被保留。
边界与常见错误
把e.event_type=Collect放WHERE会剔掉NULL行，破坏反连接。需选真实匹配时保证非空的列做IS NULL。
相关题目：Q3.1.1 · Q3.1.2
谓词

EXISTS / NOT EXISTS · 存在性判断

WHERE NOT EXISTS (SELECT 1 FROM BOOKING_EVENTS e WHERE e.vehicle_id=v.vehicle_id AND ...)

子查询至少有一行则EXISTS为true；NOT EXISTS反转。子查询投影值通常与存在性无关。

本作业中的作用
为每辆车确认不存在任何Collect事件。
输入与输出示例
教学：子查询返回NULL一行时EXISTS仍true，因为检查有无行而不是行值。
边界与常见错误
NOT IN与含NULL集合会有三值逻辑陷阱；相关子查询逻辑不强制物理重复全扫描，规划器可去相关。
相关题目：Q3.1.1 · Q3.1.2
特殊值与谓词

NULL / IS NULL / 三值逻辑

x IS NULL; x IS NOT NULL

NULL表示缺失或未知；普通比较产生unknown，不等同于空字符串或0。

本作业中的作用
无sponsor是根账号；未匹配外连接右侧是NULL；非收费事件amount为空。
输入与输出示例
教学：NULL=NULL不是true，筛空必须IS NULL；WHERE仅保留true。
边界与常见错误
COUNT(*)包含NULL行，COUNT(col)不计空值。SUM忽略空值。NOT NULL仅限制缺失，不限制字段业务合法性。
相关题目：Q1.2 · Q2.2.1 · Q3.1.1 · Q4.1.3
符号与运算符

引号 / 点号 / 括号 / ; / :: / <> / *

e.vehicle_id; 'Collect'; amount::numeric; a <> b

单引号为字符串，点号为对象/别名字段，分号终结SQL；::类型转换，<>不等，*可为所有列或COUNT行数语法。

本作业中的作用
原代码的字符串Collect、别名e/v、函数嵌套括号、EXPLAIN转录中的::text。
输入与输出示例
教学：event_type='Collect'比较列与文字；"Collect"会当区分大小写的标识符，含义不同。
边界与常见错误
括号可能是函数参数、子查询、CTE或索引表达式，按上下文判断。AND/OR遇NULL使用三值逻辑；注释--直到行末不执行。

从要求推到结论

A对每辆v检查是否存在e.vehicle_id=v.vehicle_id且event_type=Collect的事件。子查询SELECT 1只是存在性占位，找到匹配就足够；NOT EXISTS保留一个也没有的车辆。

B把Collect限制放进LEFT JOIN的ON，让每辆车尝试连接取车事件；没匹配时右侧列填NULL，再WHERE e.vehicle_id IS NULL。该字段在事件schema中NOT NULL，因此NULL可靠表示未匹配，不会误把真实事件判成无事件。

我对题目的理解是：起点必须是VEHICLES，以便连完全没有任何事件的新车也能出现。“从未Collect”不等于“目前最新不是Collect”，也不等于“没有任何事件”。 实现时，A对每辆v检查是否存在e.vehicle_id=v.vehicle_id且event_type=Collect的事件。子查询SELECT 1只是存在性占位，找到匹配就足够；NOT EXISTS保留一个也没有的车辆。 从证据看，主报告p25–26原生图：A与B均75行，各展示前10和末10，省略中间55行。截图首尾相同不能严格证明所有行相同；原有独立双向EXCEPT ALL检查可作为另一个轮次的校验证据，不冒充本轮截图。 我还会说明这个边界：NOT IN遇到子查询NULL会产生UNKNOWN，这也是不能随意替换NOT EXISTS的原因。B的Collect谓词属于匹配条件，不能错误移到结果过滤。

练习稿为学习辅助，先理解再用自己的表达说明；其中数字均保留其来源轮次。
