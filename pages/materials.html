Q4 Transactions (9 marks total) 
In PostgreSQL, a transaction is set up by surrounding the SQL commands of the transaction with 
BEGIN and COMMIT commands. For example, a banking transaction would look like: 
BEGIN; 
UPDATE accounts SET balance = balance - 100.00 
  WHERE name = 'Alice'; 
-- some more statements etc etc 
COMMIT; 
https://www.postgresql.org/docs/current/tutorial-transactions.html 
In this question we will examine what happens when two transactions occur concurrently. 
Background: how PostgreSQL reads 
You have seen two ways of keeping a concurrent schedule serialisable: locking protocols such as 
two-phase locking, and timestamp ordering. PostgreSQL uses neither of these for ordinary 
reads, so what you are about to observe will not follow from either one directly. This section gives 
you what you need; you are not expected to have met it before. 
Instead of taking read locks, a PostgreSQL query reads from a snapshot — a consistent picture 
of the database containing exactly those changes that were committed before the snapshot was 
taken. Because reading acquires no locks, readers never block writers and writers never block 
readers. 
At PostgreSQL's default isolation level, READ COMMITTED, a new snapshot is taken at the start 
of every statement. Two statements in the same transaction may therefore see different data, if 
another transaction committed in between them. 
Two consequences are worth holding on to as you work through this question: 
• 
A trigger runs inside the transaction that fired it. Any query the trigger makes is answered 
from that transaction's current snapshot. It gets no special or privileged view of the database. 
• 
A snapshot is not a lock. Reading a row records nothing and reserves nothing; it does not 
prevent another transaction from changing what you just read.
